# 让 Codex 直接调用智排 —— 说明（spec）

> 这是一份**功能说明 / 实现规格**，供你把 智排 接到 Codex（或任意 OpenAI 兼容编程助手）上。
> 你只需按此说明，用 AI 写一个「路由层」即可落地；这里**只描述怎么做，不写完整实现**。
> 核心：**Codex 对路由无感知**，只当作连了一个「智能端点」，实际请求由路由层按任务类别分发到不同模型。

## 目标 & 路由映射（三档）

每次 Codex 发来请求，路由层先**分类**，再分发到下表模型：

| 任务类别 | 路由到 | 来源 | 成本 | 判定依据 |
|---|---|---|---|---|
| **图片 / 多模态** | `deepseek-v4-flash-vision-exp` | 云端 DeepSeek | 便宜 | 本轮带图片/文档附件 |
| **简单**（日常短问答、继续上次操作） | 本地模型（如 ornith） | 本地服务 | ¥0 | 短 + 无强信号 |
| **复杂**（写代码、多步、深度分析、长文） | `deepseek-v4-flash` | 云端 DeepSeek | 便宜 | 强关键词 / 代码块 / 超长 / 多段 |
| 拿不准（弱信号区） | 用**本地模型**仲裁一句「简单/复杂」 | 本地服务 | ¥0 | 接近阈值但无强信号 |

> 相对文档《智排.md》的变化：**强通道由 pro 换成更便宜的 `flash`**；**图片单独走 `flash-vision-exp`**（原来归入「复杂→强模型」）。这样日常对话几乎全部落在本地免费，只有重活和看图才花一点钱，且都用 flash 档。

## 判定顺序（沿用已有启发式，优先级：图片 > 关键词 > 长度）

1. 带图片/文档附件 → `deepseek-v4-flash-vision-exp`
2. 空文本 → 本地模型（工具链续步，最便宜）
3. 含代码块 `` ``` `` → `deepseek-v4-flash`
4. 命中强关键词（设计/架构/重构/调试/根因/优化/性能/安全/为什么/如何实现/逐步…）→ `deepseek-v4-flash`
5. ≥2 段落 → `deepseek-v4-flash`
6. 超长（如 >160 字 / >28 词，中文按无空格折算）→ `deepseek-v4-flash`
7. 弱信号区（接近阈值但无强信号）→ 本地模型仲裁 → 简单/复杂
8. 其余 → 本地模型

> ⚠️ 分类**不只按字数**：附件的优先级最高（直接进 vision 档），强关键词与代码块其次，长度只是兜底。

## Codex「直接调用」的三种接入方式

| 方案 | 做法 | 优点 | 缺点 | 适合 |
|---|---|---|---|---|
| **A. 路由代理（推荐）** | 本地起一个 OpenAI 兼容**代理**，Codex 只把 `base_url` 指向它；代理收到请求→分类→转发到对应上游模型 | Codex 完全无感知、无需改 Codex 代码；一处集中管理 | 需要多写一个代理服务 | 「让 Codex 直接调用」的最贴合落地 |
| B. 静态配置分流 | 在 Codex 的配置里，把不同用途/工具固定指定到不同模型 | 最简单，零额外服务 | 是**人工静态**分流，不是按内容动态判 | 已确定用途的固定场景 |
| C. 工具回调注入路由 | 在 Codex 的 tool 回调里，按本轮内容动态选模型 | 动态、精准 | 侵入 Codex 流程，改动大 | 有源码可改的场景 |

> 建议 **方案 A**：Codex 把代理当普通 OpenAI 端点，代理内部就是「智排逻辑 + 三档上游」。Codex 那边只改一行 `base_url`，即实现「直接调用智排」。

## 代理内部的数据流（参考伪代码）

```
收到 Codex 请求 {model, messages}
  ├─ 若消息里含图片/多模态 part → target = deepseek-v4-flash-vision-exp
  └─ 否则用最后一条 user 文本做 classify：
       ├─ 简单            → target = 本地模型
       ├─ 复杂            → target = deepseek-v4-flash
       └─ 弱信号区        → 先问本地模型「简单/复杂」→ 据此选 本地 或 flash
  改写 target
  把请求转发到 target 对应的 (endpoint, api_key, model)
  ── 流式返回给 Codex
```

## 每个槽位要配什么（3 个上游槽位）

```jsonc
// 本地模型（简单通道 + 仲裁大脑；本地通常用固定占位 key）
"local": {
  "endpoint": "http://127.0.0.1:8099/v1",     // 换成你真实在跑的本地服务端口
  "api_key":  "local-noauth",                 // 本地认证占位
  "model":    "ornith-1.5-35b"                // 换成实际本地模型名
},
// 文本复杂通道
"flash": {
  "endpoint": "https://api.deepseek.com/v1",
  "api_key":  "<deepseek 密钥>",
  "model":    "deepseek-v4-flash"
},
// 图片 / 多模态通道
"vision": {
  "endpoint": "https://api.deepseek.com/v1",
  "api_key":  "<deepseek 密钥>",
  "model":    "deepseek-v4-flash-vision-exp"
}
```

**分类阈值**（可选）：

```jsonc
{
  "max_chars": 160,      // 中文按字数、英文按字符数
  "max_words": 28,       // 中文无空格按 字数<->词数×2 折算
  "arbitrate": true      // 弱信号区是否让本地模型仲裁
}
```

## 落地清单（给写代码的 AI 或开发者）

1. 实现 `classify(text, has_image)` —— 按上文判定顺序返回 `simple / strong / vision / unsure`。
2. 实现 `resolve()` —— 把 decision 映射到目标槽位；`unsure` 时先调本地模型仲裁。
3. 实现一个 OpenAI 兼容的 `POST /v1/chat/completions`（含 SSE 流式透传），内部按 `resolve` 选上游并**透传**请求/响应，不改动 Codex 看到的消息格式。
4. 三个槽位做**健康检查 / 兜底**：本地失败→切 `flash`；flash 失败→报错（或再上一档）。别让本地挂掉时反复重试。
5. 用真实请求各测一次：短问题→本地、长/难→`flash`、带图→`vision-exp`。

## 验证点

- **普通问一句**「解释这行」 → 命中本地，`api_key` 为 local、无云端 token 消耗，返回快、无成本。
- **写代码 / 长需求**「实现一个带并发安全的缓存」→ 命中 `flash`。
- **上传一张图**「看下这张图里是什么」→ 命中 `vision-exp`。
- **本地服务停掉** → 自动切 `flash`，对话不中断（但会产生少量云端费用）。
- 在状态栏核对：本轮命中模型是否与预期一致。

## 一句话

> 给 Codex 套一个**「智能端点」**：图片→`vision-exp`、复杂→`flash`、其余→本地免费模型，拿不准→本地仲裁。Codex 只改 `base_url` 即可「直接调用智排」，你只需按此 spec 写一个路由代理。
